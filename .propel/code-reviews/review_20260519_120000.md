## High Severity Issues

### [Security / A01 + A07] Missing `/login` Route — ProtectedRoute Redirect Broken in Production

**File**: `frontend/src/App.tsx:1`
**Severity**: HIGH

**Issue Description**:
`ProtectedRoute` redirects unauthenticated users to `/login` via `<Navigate to="/login" ... />`.
The `App.tsx` router registers three routes: `/intake/:appointmentId`, `/documents/upload`,
and `/`. No `/login` route is registered. When an unauthenticated user is served a production
build and attempts to access a protected route, React Router v6 renders nothing (no matched
route) resulting in a blank page with no error, no call to action, and no fallback.

This is a re-registration of finding **F009** (2026-05-19). The risk has increased in this
commit because `ProtectedRoute` is now wired into the router (whereas previously no protection
existed at all). In DEV mode the `import.meta.env.DEV` bypass masks the issue entirely.

**Code Snippet**:

```tsx
// frontend/src/App.tsx — current routes
<Routes>
  <Route path="/intake/:appointmentId" element={<ProtectedRoute><IntakePage /></ProtectedRoute>} />
  <Route path="/documents/upload" element={<ProtectedRoute><DocumentUploadPage /></ProtectedRoute>} />
  <Route path="/" element={<main><BaselineDemo /></main>} />
  {/* No /login route */}
</Routes>
```

**Impact**:
In any production build, unauthenticated access to `/intake/*` or `/documents/upload`
produces a blank white page. The user has no path to recover or log in. This breaks the
entire authenticated workflow and violates OWASP A01 (Broken Access Control) and A07
(Authentication Failures).

**Fix Recommendation**:
Register a `/login` route before US_010 is complete. A minimal stub that prevents the
blank page is sufficient until the real login page is built.

```tsx
// App.tsx — add placeholder login route
import { LoginPage } from './pages/LoginPage'; // stub or real

<Routes>
  <Route path="/login" element={<LoginPage />} />
  <Route path="/intake/:appointmentId" element={<ProtectedRoute><IntakePage /></ProtectedRoute>} />
  <Route path="/documents/upload" element={<ProtectedRoute><DocumentUploadPage /></ProtectedRoute>} />
  <Route path="/" element={<main><BaselineDemo /></main>} />
</Routes>
```

Minimum stub (if US_010 is not yet available):

```tsx
// frontend/src/pages/LoginPage.tsx — temporary stub
export function LoginPage(): JSX.Element {
  return <main><p>Login coming soon (US_010).</p></main>;
}
```

**References**:
- OWASP A01: Broken Access Control — https://owasp.org/Top10/A01_2021-Broken_Access_Control/
- OWASP A07: Identification and Authentication Failures — https://owasp.org/Top10/A07_2021-Identification_and_Authentication_Failures/
- Registry finding: F009

## Medium Severity Issues

### [Security / A07] No `AuthProvider` Wrapping App — All API Calls Are Unauthenticated

**File**: `frontend/src/App.tsx:1`
**Severity**: MEDIUM

**Issue Description**:
`useAuth()` is consumed in `ProtectedRoute`, `IntakePage`, and `useAIIntake`. Without an
`AuthProvider` wrapping the component tree, all three consumers receive the default context
value (typically `{ token: null, user: null }`). This means `buildHeaders()` omits the
`Authorization` header, and all API calls to `/api/v1/intake/*` are unauthenticated. The
backend would reject them with 401. This is F004 (2026-05-18) which remains unresolved.

**Fix Recommendation**:
Wrap `<App />` with `<AuthProvider>` in `main.tsx` or directly in `App.tsx`:

```tsx
// main.tsx
import { AuthProvider } from './context/AuthContext';
root.render(<AuthProvider><App /></AuthProvider>);
```

### [Security / A05] `"AllowedHosts": "*"` in `appsettings.json`

**File**: `backend/src/UPACIP.API/appsettings.json:8`
**Severity**: MEDIUM

**Issue Description**:
`"AllowedHosts": "*"` accepts any host header value, exposing the API to Host Header
Injection attacks if deployed without a reverse proxy that restricts the `Host` header.
This is acceptable in `appsettings.json` (development config), but this file is committed
and may be used as a baseline for production if `appsettings.Production.json` is not
correctly overriding it.

**Fix Recommendation**:
Set `"AllowedHosts": "*"` only in `appsettings.Development.json`. Ensure `appsettings.Production.json`
sets the explicit allowed hostnames:

```json
// appsettings.Production.json
{
  "AllowedHosts": "patient-portal.example.com"
}
```

**File**: `frontend/src/components/auth/ProtectedRoute.tsx:18`
**Severity**: MEDIUM

**Issue Description**:

## Low Severity Issues

### [Quality] `submitAnswer` Lacks AbortController

**File**: `frontend/src/hooks/useAIIntake.ts:222`
**Issue**: `submitAnswer` issues a `fetch` without an `AbortController`. If the `AIIntakeChat`
component unmounts while the request is in-flight (e.g., user switches to manual mode mid-answer),
the network request completes and the response handler runs — resulting in state updates
on a no-longer-mounted instance. React 18 does not throw on unmounted `setState` calls, but
the wasted network round-trip is avoidable.
**Fix**: Create an `AbortController` in `submitAnswer` (parallel to the `startSession` pattern
already in the hook) and abort it in the callback's cleanup or on component unmount via `useRef`.

---

### [Security] `JSON.parse` Without Runtime Validation in `loadFromStorage`

**File**: `frontend/src/hooks/useAIIntake.ts:70`
**Issue**: `JSON.parse(raw) as Partial<IntakeSessionState>` is a TypeScript type cast with no
runtime schema guard. SessionStorage is same-origin only, so an attacker would require XSS
access to inject malicious data. If poisoned, the parsed value is used to restore UI state
(`capturedFields`, `method`), which could produce unexpected rendering. PHI values are already
stripped before storage (`stripPhiValues`) so no PHI leakage risk.
**Fix**: Add a minimal guard to validate the parsed object's shape before using it:

```typescript
function isValidStoredState(obj: unknown): obj is Partial<IntakeSessionState> {
  if (typeof obj !== 'object' || obj === null) return false;
  const s = obj as Record<string, unknown>;
  return !s.capturedFields || Array.isArray(s.capturedFields);
}
```

**Note**: The `srOnly` constant is defined at module scope as a `React.CSSProperties` object

### [UX] Confirmed State Resets on Re-navigation

**File**: `frontend/src/pages/IntakePage.tsx:93`
**Note**: After `setConfirmed(true)`, if the patient navigates away and back to
`/intake/:appointmentId`, the component remounts with `confirmed = false` (React state
does not persist across unmounts). `startSession` will attempt to resume — the backend
may return an already-confirmed session but the frontend has no check to detect and display
a "Intake already submitted" state instead of the form.
**Suggestion**: On session resume, check backend response for a `confirmed: true` signal
and short-circuit to the confirmed view rather than the conversation view.

## Improvement Suggestions

### Replace `capturedFields` Dependency in `submitAnswer` with Functional Updater

**Area**: Performance / React rendering
**Benefit**: Eliminates `capturedFields` from `submitAnswer`'s `useCallback` dependency array,
preventing AIIntakeChat from re-rendering on every captured-field state update.
**Effort**: Low

**Details**:
`submitAnswer` uses `capturedFields` to compute `updatedFields`. This can be rewritten using
a functional updater form of `setCapturedFields`, removing the state value from the closure:

**Example**:

```typescript
// Before
const updatedFields: CapturedField[] = [
  ...capturedFields.filter((f) => f.fieldKey !== currentFieldKey),
  { fieldKey: currentFieldKey, fieldLabel: currentFieldKey, value: rawAnswer, manualRequired: false },
];
setCapturedFields(updatedFields);

// After — no capturedFields in dependency array
setCapturedFields((prev) => [
  ...prev.filter((f) => f.fieldKey !== currentFieldKey),
  { fieldKey: currentFieldKey, fieldLabel: currentFieldKey, value: rawAnswer, manualRequired: false },
]);
```
