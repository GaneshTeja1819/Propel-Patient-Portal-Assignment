## High Issues

### CR-002

**Severity:** HIGH  
**Category:** Security — A07 Authentication Failures  
**File:** `frontend/src/App.tsx` lines 7–22  
**Relates to:** Registry F010 (unresolved)

**Description:**  
`App.tsx` wraps routes in `BrowserRouter` but does not wrap the application in an `AuthProvider`. The `AuthContext` is consumed by `useAuth()` inside `ProtectedRoute` and `IntakePage`. Without `AuthProvider`, `useAuth()` returns the module-level `devDefault` constant (a DEV stub with a mock token and user) rather than any real authentication state.

In production builds where `import.meta.env.DEV === false`, the dev stub still provides `token: null` and `user: null` — meaning **all API calls from `useAIIntake` will be sent without a Bearer token** (the `Authorization` header will be `"Bearer null"`), and all intake pages will trigger the ProtectedRoute redirect to `/login`.

**Current `App.tsx`:**
```tsx
function App() {
  return (
    <BrowserRouter>
      <Routes>
        <Route path="/intake/:appointmentId" element={<ProtectedRoute><IntakePage /></ProtectedRoute>} />
        <Route path="/" element={<main><BaselineDemo /></main>} />
      </Routes>
    </BrowserRouter>
  );
}
```

**Required fix:**
```tsx
// Wrap with <AuthProvider> once US_010 delivers it
// For now, ensure the mock provider is applied in tests
function App() {
  return (
    <AuthProvider>  {/* ADD — to be delivered in US_010 */}
      <BrowserRouter>
        <Routes>...</Routes>
      </BrowserRouter>
    </AuthProvider>
  );
}
```

### CR-003

**Severity:** HIGH  
**Category:** Security — A01 Broken Access Control  
**File:** `frontend/src/App.tsx` line 16  
**Relates to:** Registry F009 (escalated — ProtectedRoute now active)

**Description:**  
`ProtectedRoute` redirects unauthenticated users to `/login`. No `/login` route is registered in `App.tsx`. React Router v6 renders `null` for unmatched paths with no fallback `<Route path="*">`, producing a silent blank page. In production environments (where the DEV bypass in `ProtectedRoute` does NOT apply), any unauthenticated access to `/intake/*` will silently redirect to blank.

**Required fix:** Register the login route or a catch-all redirect:
```tsx
<Route path="/login" element={<LoginPage />} />  {/* US_010 */}
<Route path="*" element={<Navigate to="/" replace />} />  {/* fallback */}
```

### CR-004

**Severity:** HIGH  
**Category:** Code Quality — Resource Leak / React State Safety  
**File:** `frontend/src/hooks/useAIIntake.ts` lines 119–122

**Description:**  
`startSession()` creates an `AbortController` for the `fetch` call chain but never calls `ac.abort()`. No `useEffect` cleanup function is returned by `IntakePage`. This means:

1. If the component unmounts mid-request (e.g., user navigates away), the fetch continues in the background.
2. When the fetch completes, `setState` calls (`setAiState(...)`) are invoked on the unmounted component, triggering the React warning `"Can't perform a React state update on an unmounted component"`.
3. In React StrictMode (development), `useEffect` runs twice — two simultaneous intake session `POST` calls are made.

```ts
// useAIIntake.ts:119
const ac = new AbortController();
const { signal } = ac;
// ... fetch('/api/v1/intake/start', { signal })
// ac.abort() is NEVER called
```

**Required fix:**
```ts
// Expose abort from startSession, or manage it inside the hook's own state:
const abortRef = useRef<AbortController | null>(null);

// In startSession:
abortRef.current?.abort();
const ac = new AbortController();
abortRef.current = ac;

// Return cleanup from useEffect in IntakePage:
useEffect(() => {
  if (mode === 'ai') startSession();
  return () => { /* call abort when hook exposes it */ };
}, []);
```

### CR-005

**Severity:** HIGH  
**Category:** Security — A07 Authentication Failures  
**File:** `frontend/src/components/auth/ProtectedRoute.tsx` line 20

**Description:**  
`ProtectedRoute` contains a compile-time conditional that unconditionally bypasses all authentication checks in development environments:

```tsx
// DEV bypass: allow access without login until US_010 login page is built.
if (import.meta.env.DEV) return children;
```

While Vite's build system statically replaces `import.meta.env.DEV` with `false` in production bundles (making this safe for correctly configured production builds), the risk surface is:

- **Staging/CI environments** where `NODE_ENV=development` or `VITE_DEV=true` might be set without intent.
- **Build toolchain misconfiguration** (e.g., Webpack-based build fallback, test harness that doesn't configure Vite mode).
- **Supply chain attack** where the build environment is compromised and switches the mode.

The bypass is not gated by a specific feature flag or a named constant that makes the intent unambiguous — any `DEV=true` environment silently disables all route authentication.

**Recommendation:** Replace the unconditional DEV bypass with an explicit feature flag (`import.meta.env.VITE_AUTH_BYPASS_ENABLED`), or add a console warning that is visually prominent when the bypass is active.

### CR-010

**Severity:** LOW  
**Category:** Performance  
**File:** `frontend/src/pages/IntakePage.tsx` line 165

**Description:**  
`displayInitials` is a derived value computed via string manipulation on every render:

```tsx
const displayInitials = user?.displayName
  ?.split(' ')
  .map((n) => n[0])
  .join('')
  .toUpperCase() ?? '?';
```

This is a pure derivation from a stable `user` reference. It should be memoized with `useMemo` to avoid repeated string allocation on every render cycle (e.g., during AI streaming updates that trigger frequent re-renders).

**Recommended fix:**
```tsx
const displayInitials = useMemo(
  () => user?.displayName?.split(' ').map((n) => n[0]).join('').toUpperCase() ?? '?',
  [user?.displayName],
);
```

## Informational Notes

### CR-011

**Severity:** INFO  
**Category:** Architecture  
**File:** `frontend/src/hooks/useAIIntake.ts` line 324

**Description:**  
`confirmIntake()` sends the full `capturedFields` array (including all PHI values) to `POST /api/v1/intake/confirm`. There is no client-side guard on the total payload size. On very long intake sessions with many fields, or if a user enters unusually long free-text answers, the payload could exceed nginx/IIS default body size limits (typically 1–4 MB), causing a 413 response with no user-visible error message.

**Recommendation:** Add a payload size estimate check before the fetch call, or ensure the backend controller returns a meaningful 413 response body that `confirmIntake` error handling surfaces to the UI.

## Architecture Review

### Component Architecture

The commit introduces a clean three-layer frontend architecture for the intake feature:

```
IntakePage (page / orchestration layer)
  └── useAIIntake (data / state layer — all API calls)
      └── AuthContext (cross-cutting auth)
  └── AIIntakeChat (presentation — not in this commit)
  └── IntakeSummaryReview (presentation — not in this commit)
  └── IntakeProgressBar (presentation — not in this commit)
```

This separation is well-designed. `IntakePage` contains no direct fetch calls and delegates all API interactions to `useAIIntake`. The hook manages both the server state (session, current question, errors) and the UI state (loading flags).

### Authentication Architecture Gap

The `AuthContext` is a module-level constant (`devDefault`) rather than a provider-provided value. This means React's context system is bypassed — `useAuth()` always returns the same object regardless of the component tree. The `AuthProvider` (US_010 deliverable) must wrap `App` before `ProtectedRoute` can function correctly in production.

### Session State Architecture

The `mode` persistence (AI vs. manual) via `sessionStorage` is well-scoped. The `stripPhiValues` approach for storage is architecturally sound — it persists UI progress (which sections are open, mode, appointment ID) without persisting PHI. The confirmIntake flow correctly clears sessionStorage on success, preventing data residue after completion.

## Technology-Specific Analysis

### Frontend (React 18 / TypeScript 5.9 / Vite 5)

- **React 18 Concurrent Mode**: The lack of `AbortController` cleanup (CR-004) is particularly problematic in React 18 with `StrictMode`, which double-invokes effects in development. The `AbortError` suppression in `startSession` mitigates one symptom but does not solve the root issue.
- **Vite ENV handling**: `import.meta.env.DEV` is correctly used for compile-time conditionals. Vite's tree-shaking will correctly eliminate the DEV bypass block in production bundles. However, the absence of a named feature flag makes this harder to audit in CI.
- **TypeScript strictness**: 0 type errors with `strict: true` (inferred from tsconfig). The hook return type is well-typed via `UseAIIntakeReturn` interface.
- **React Router v6**: Correct use of `<Navigate>` with `replace` to avoid back-button pollution. The `useLocation` state pattern for post-auth redirect is idiomatic.

### Backend (ASP.NET Core 10 / .NET 10)

- **Configuration management**: The `appsettings.json` change is structurally correct but the history exposure (CR-001) remains the blocking issue. The .NET configuration system's environment variable override (`ConnectionStrings__DefaultConnection`) is not documented.
- **No backend-only changes**: The three backend files reviewed (`appsettings.json`, `appsettings.Development.json`, `Program.cs`) are configuration/infrastructure only. No new controller logic was added in this commit.
- **Hangfire Dashboard**: The empty-string password replacement (CR-008) is an improvement over the prior commit's open dashboard, but is still exploitable if env vars are not set.
