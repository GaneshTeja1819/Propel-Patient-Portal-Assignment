## Critical Issues

### [Security] Broken Appointment Ownership — Any Patient Can Hijack Any Session

**File**: `backend/src/UPACIP.API/Controllers/IntakeController.cs:148`
**Severity**: CRITICAL

**Issue Description**:
`ValidateAppointmentOwnership()` only verifies that the JWT `sub` claim is present and
that `appointmentId != Guid.Empty`. It does **not** verify that the appointment referenced
in the request belongs to the authenticated patient. Any valid JWT holder can pass an
arbitrary `AppointmentId` to `POST /intake/start`, `POST /intake/answer`, or
`GET /intake/session/{id}` and read or manipulate another patient's session.

**Code Snippet**:

```csharp
private bool ValidateAppointmentOwnership(Guid appointmentId)
{
    var sub = User.FindFirstValue("sub");
    return !string.IsNullOrWhiteSpace(sub) && appointmentId != Guid.Empty;
}
```

**Impact**:
OWASP A01 — Broken Access Control. An authenticated patient can enumerate appointment IDs
(e.g., sequential GUIDs or leaked IDs) and access, overwrite, or read the intake session
data of other patients, including PHI captured fields.

**Fix Recommendation**:
Query the `Appointment` entity via `IUnitOfWork` and assert that
`appointment.PatientId == parsedSub`. This is planned for task_003 per the code comment;
it must be implemented before merging or the endpoint must be disabled/gated until task_003
lands.

**Code Example**:

```csharp
private async Task<bool> ValidateAppointmentOwnershipAsync(Guid appointmentId)
{
    var sub = User.FindFirstValue("sub");
    if (string.IsNullOrWhiteSpace(sub) || appointmentId == Guid.Empty) return false;

    // Resolve patient from sub claim
    if (!Guid.TryParse(sub, out var patientId)) return false;

    var appointment = await _unitOfWork.Appointments.GetByIdAsync(appointmentId);
    return appointment is not null && appointment.PatientId == patientId;
}
```

If task_003 is not yet ready, add a feature flag or return `501 Not Implemented` until the
ownership check is wired.

**References**:
- OWASP A01:2021 Broken Access Control — https://owasp.org/Top10/A01_2021-Broken_Access_Control/
- UPACIP task_003 (ownership check deferred)

## High Severity Issues

### [Security] Newtonsoft.Json 11.0.1 — Known HIGH Vulnerability (GHSA-5crp-9r3c-p9vr)

**File**: `backend/src/UPACIP.Infrastructure/UPACIP.Infrastructure.csproj` and `backend/src/UPACIP.API/UPACIP.API.csproj`
**Severity**: HIGH

**Issue Description**:
`dotnet list package --vulnerable` reports `Newtonsoft.Json 11.0.1` with a known **HIGH**
severity vulnerability (GHSA-5crp-9r3c-p9vr — ReDoS in date parsing). This affects both
`UPACIP.Infrastructure` and `UPACIP.API`.

**Code Snippet**:

```xml
<!-- UPACIP.Infrastructure.csproj -->
<PackageReference Include="Newtonsoft.Json" Version="11.0.1" />
```

**Impact**:
A maliciously crafted date string input to any endpoint that deserialises JSON via
`Newtonsoft.Json` could cause CPU exhaustion (ReDoS). On a healthcare patient portal this
is a viable targeted DoS vector.

**Fix Recommendation**:
Upgrade `Newtonsoft.Json` to `>= 13.0.3` (the minimum patched version). Where possible,
migrate serialisation to `System.Text.Json` (already used in `IntakeSessionService`).

**References**:
- GHSA-5crp-9r3c-p9vr — https://github.com/advisories/GHSA-5crp-9r3c-p9vr
- OWASP A06:2021 Vulnerable and Outdated Components

### [AI/LLM Security] No Rate Limiting on Gemini API Calls Per Session

**File**: `backend/src/UPACIP.Infrastructure/AI/GeminiIntakeAdapter.cs` and `backend/src/UPACIP.API/Controllers/IntakeController.cs`
**Severity**: HIGH

**Issue Description**:
`POST /intake/answer` calls `GeminiIntakeAdapter.CallFieldAsync` on every request with no
per-session or per-user rate limit. With 8 fields and a 1-retry policy, a legitimate
session makes up to 16 Gemini calls. However, nothing prevents a patient (or a script
abusing a stolen JWT) from sending thousands of answers per minute, generating unbounded
Gemini API cost and a potential application-layer DoS.

**Code Snippet**:

```csharp
// No rate-limit guard before this call
var result = await _intakeService.SubmitAnswerAsync(
    request.AppointmentId, request.FieldKey, trimmedAnswer, ct);
```

**Impact**:
Unbounded Gemini API spend; application-layer DoS; potential for intentional cost
exhaustion against the service (OWASP A04 — Insecure Design, AI/LLM rate limiting).

**Fix Recommendation**:
Add a per-appointment answer-count limit in `IntakeSessionService` (e.g., max 24 answers
per session = 8 fields × 3 retries). Reject with `429 Too Many Requests` when exceeded.
Also add an ASP.NET Core rate-limiting policy on the `/answer` endpoint.

**References**:
- OWASP LLM04 — Model Denial of Service (OWASP LLM Top 10)
- ASP.NET Core Rate Limiting — https://learn.microsoft.com/en-us/aspnet/core/performance/rate-limit

## Medium Severity Issues

### [Security] Silent Answer Truncation Without Client Notification

**File**: `backend/src/UPACIP.API/Controllers/IntakeController.cs:86`
**Severity**: MEDIUM

**Issue Description**:
Answers longer than 2000 characters are silently truncated: `trimmedAnswer[..MaxAnswerLength]`.
The controller proceeds and returns `200 OK` as if the full answer was processed. The patient
has no indication that their response was cut off, which could result in incomplete or
incorrect PHI being captured in the intake record.

**Fix Recommendation**:
Return `400 Bad Request` with an informative message rather than silently truncating:

```csharp
if (trimmedAnswer.Length > MaxAnswerLength)
    return BadRequest(new { message = $"Answer must be {MaxAnswerLength} characters or fewer." });
```

### [Architecture] `CapturedFieldDto` Missing `IsPhiField` Flag

**File**: `backend/src/UPACIP.API/Controllers/IntakeController.cs:210`
**Severity**: MEDIUM

**Issue Description**:
`CapturedFieldDto` exposes `Value` (the captured field data) but has no `IsPhiField`
property. The frontend summary review (`IntakeSummaryReview.tsx`) cannot determine which
returned values are PHI without re-fetching the question list or hard-coding field names.
This prevents correct masking, display, and audit annotation of PHI values.

**Fix Recommendation**:
Add `bool IsPhiField` to `CapturedFieldDto` and populate it in both response sites:

```csharp
public sealed record CapturedFieldDto(
    string FieldKey,
    string FieldLabel,
    string Value,
    bool ManualRequired,
    bool IsPhiField);   // <-- add
```

Populate from `_phiFieldKeys.Contains(f.FieldKey)` in service response builders.

### [Quality] `ValidateAppointmentOwnership` Name is Misleading

**File**: `backend/src/UPACIP.API/Controllers/IntakeController.cs:142`
**Severity**: MEDIUM

**Issue Description**:
The method name `ValidateAppointmentOwnership` implies it performs a full ownership check.
The implementation only validates that the caller has an authenticated `sub` claim and the
ID is not empty. Any reader will assume the ownership check is complete and not add a
second guard. This is a readability/safety anti-pattern.

**Fix Recommendation**:
Rename to `IsRequestAuthenticated(Guid appointmentId)` or add a clear
`// TODO (task_003): full ownership check` comment inline. Remove the misleading name.
