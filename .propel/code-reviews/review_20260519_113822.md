## High Severity Issues

### [Architecture] Missing `/login` route — ProtectedRoute redirect target does not exist

**File**: `frontend/src/App.tsx:10-22`  
**Severity**: HIGH

**Issue Description**:
`ProtectedRoute` redirects unauthenticated users to `/login` (via `<Navigate to="/login" ...>`), but `App.tsx` does not define a `<Route path="/login">`. In React Router v6, `<Routes>` renders `null` when no route matches — the patient sees a blank page, the error banner never renders, and the auth recovery path is completely broken.

**Code Snippet**:
```tsx
// App.tsx — all registered routes
<Routes>
  <Route
    path="/intake/:appointmentId"
    element={<ProtectedRoute><IntakePage /></ProtectedRoute>}
  />
  <Route path="/" element={<main><BaselineDemo /></main>} />
  {/* ← No /login route */}
</Routes>
```

**Impact**:
Any unauthenticated patient navigating to `/intake/:id` is silently redirected to `/login` which renders nothing. This completely blocks the intake flow and provides no recovery UX. When US_010 (LoginPage) is delivered, a missing route registration will cause the same blank-screen failure unless this is addressed proactively.

**Fix Recommendation**:
Register a `/login` route now — even a placeholder — so the redirect lands safely. The `state.from` passed by ProtectedRoute allows post-login redirect-back.

**Code Example**:
```tsx
import { LoginPage } from './pages/LoginPage'; // US_010 — or a placeholder

<Routes>
  <Route path="/login" element={<LoginPage />} />
  <Route
    path="/intake/:appointmentId"
    element={<ProtectedRoute><IntakePage /></ProtectedRoute>}
  />
  <Route path="/" element={<main><BaselineDemo /></main>} />
  <Route path="*" element={<Navigate to="/" replace />} />
</Routes>
```

**References**:
- React Router v6: [No-match (404) routes](https://reactrouter.com/en/main/start/tutorial#handling-not-found-errors)
- OWASP A07: Authentication Failures

## Medium Severity Issues

### [Security] `AllowedHosts: "*"` accepts any host header (OWASP A05)

**File**: `backend/src/UPACIP.API/appsettings.json:8`  
**Severity**: MEDIUM

**Issue Description**:
`"AllowedHosts": "*"` disables ASP.NET Core's Host header filtering entirely. In production, this permits Host header injection attacks: a malicious request with a crafted `Host` header can influence password-reset links, server-generated URLs, cache poisoning, and DNS rebinding exploits.

**Fix Recommendation**:
Restrict `AllowedHosts` to the known production domain(s). Use environment-specific override in `appsettings.Production.json`.

```json
{
  "AllowedHosts": "patientportal.example.com;api.patientportal.example.com"
}
```

### [Architecture] AbortController in `startSession` not aborted on component unmount

**File**: `frontend/src/hooks/useAIIntake.ts:119-209`  
**Severity**: MEDIUM

**Issue Description**:
`startSession` creates an `AbortController` locally but the `useEffect` in `IntakePage.tsx` that calls `startSession()` has no cleanup function returning `ac.abort()`. If the component unmounts while the fetch is in flight (navigation, session timeout), the request completes and triggers `setState` calls on an unmounted component. React 18 suppresses the "state update on unmounted component" warning, but the fetch continues consuming network resources and may log misleading state transitions.

**Fix Recommendation**:
Return the abort function from `startSession` (or expose an `abortSession` method) and call it in the `useEffect` cleanup.

```tsx
// IntakePage.tsx
const abortRef = useRef<(() => void) | null>(null);

useEffect(() => {
  if (mode === 'ai') {
    const abort = startSession(); // startSession returns abort fn
    abortRef.current = abort;
  }
  return () => abortRef.current?.();
  // eslint-disable-next-line react-hooks/exhaustive-deps
}, []);
```

```typescript
// useAIIntake.ts — startSession returns cleanup fn
const startSession = useCallback((): (() => void) => {
  const ac = new AbortController();
  // ... existing logic ...
  return () => ac.abort();
}, [appointmentId, buildHeaders]);
```

### [Security] `loadFromStorage` casts parsed JSON without structural validation (A08)

**File**: `frontend/src/hooks/useAIIntake.ts:79-83`  
**Severity**: MEDIUM

**Issue Description**:
`JSON.parse(raw) as Partial<IntakeSessionState>` uses a TypeScript type assertion (`as`) which provides no runtime guarantee. If sessionStorage has been tampered with (XSS, or manual manipulation), a malformed object is accepted silently and spread into React state, potentially causing runtime errors or unexpected UI behaviour.

**Fix Recommendation**:
Add a lightweight structural guard before consuming the parsed value.

```typescript
function isValidStoredState(v: unknown): v is Partial<IntakeSessionState> {
  if (!v || typeof v !== 'object') return false;
  const obj = v as Record<string, unknown>;
  // Validate only the fields we actually read from storage
  if (obj.capturedFields !== undefined && !Array.isArray(obj.capturedFields)) return false;
  if (obj.method !== undefined && !['AI', 'AI-Partial', 'Manual'].includes(obj.method as string)) return false;
  return true;
}

function loadFromStorage(appointmentId: string): Partial<IntakeSessionState> | null {
  try {
    const raw = sessionStorage.getItem(storageKey(appointmentId));
    if (!raw) return null;
    const parsed: unknown = JSON.parse(raw);
    return isValidStoredState(parsed) ? parsed : null;
  } catch {
    return null;
  }
}
```

### [Quality] `submitAnswer` has no AbortController — in-flight requests uncontrolled

**File**: `frontend/src/hooks/useAIIntake.ts:226-312`  
**Issue**: `submitAnswer` fires a `fetch` with no AbortController. A slow network response can complete after the user has switched to manual mode or navigated away, triggering state updates that conflict with the new UI state. The `phase` guard (`if (!currentFieldKey || phase !== 'conversation') return`) only prevents new calls; it does not cancel in-flight ones.  
**Fix**: Follow the same AbortController pattern used in `startSession`; store the controller ref so mode-switch can abort any pending request.

### [Quality] `JSX.Element` return type deprecated in React 19

**File**: `frontend/src/pages/IntakePage.tsx` (lines 62, 84), `frontend/src/components/auth/ProtectedRoute.tsx:13`  
**Issue**: `JSX.Element` as an explicit return type is deprecated in the React 19 typings, which align return types with `ReactNode`. TypeScript currently infers these correctly, but explicit annotations using `JSX.Element` will produce warnings when upgrading to React 19.  
**Fix**: Replace `JSX.Element` with `React.ReactElement` (for components that never return null) or `React.ReactNode` (for the general case).
