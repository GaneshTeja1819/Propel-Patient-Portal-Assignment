**Required fix:** Wrap `BrowserRouter` with the real `AuthProvider` from US_010 when delivered, or at minimum with a `AuthContext.Provider` that initialises from `localStorage`/cookie for interim use.

### CR-004

**Severity:** 🟠 HIGH
**File:** `frontend/src/hooks/useAIIntake.ts`
**Lines:** 119–125, 208–212 (IntakePage.tsx)
**Category:** Quality / HIPAA — React lifecycle
**Registry:** F014

**Issue:** An `AbortController` is created at the start of `startSession`, and its `signal` is passed to the two `fetch()` calls inside the function. However, `ac.abort()` is **never called**. The controller is a local variable that goes out of scope at the end of `startSession`. The signal never fires; the fetch calls behave identically to calls without a signal.

**Additionally**, `IntakePage.tsx` calls `startSession()` in a `useEffect` with no cleanup return:
```tsx
useEffect(() => {
  if (mode === 'ai') {
    startSession();  // no AbortController returned; no cleanup
  }
  // eslint-disable-next-line react-hooks/exhaustive-deps
}, []);
```

React 18 Strict Mode double-invokes `useEffect` in development, sending two POST requests to `/api/v1/intake/start`. In production, if the component unmounts before the fetch resolves (e.g., route change), `setCapturedFields`, `setMessages`, and `setPhase` all run on an unmounted component.

**The comment in the code is factually incorrect:**
```ts
// N-004: AbortController prevents React StrictMode double-invoke side-effects
const ac = new AbortController();
```
This does **not** prevent double-invoke because `ac.abort()` is never called.

**Required fix:**
```ts
// In useAIIntake.ts — expose a cleanup function or return the controller
// Option A: use a ref in the hook to track and cancel
const abortRef = useRef<AbortController | null>(null);

// Inside startSession:
abortRef.current?.abort();
const ac = new AbortController();
abortRef.current = ac;

// Add useEffect cleanup:
useEffect(() => {
  return () => { abortRef.current?.abort(); };
}, []);

// In IntakePage.tsx useEffect:
useEffect(() => {
  if (mode === 'ai') startSession();
  return () => { /* call abort */ };
}, []);
```

### CR-008

**Severity:** 🟡 MEDIUM
**File:** `frontend/src/pages/IntakePage.tsx`
**Lines:** 92–96
**Category:** Accessibility — WCAG 2.4.2 Page Titled

**Issue:** The `document.title` effect has only one dependency (`confirmed`) and always uses the string `'AI Intake | Patient Portal'` for the non-confirmed state, regardless of `mode`:

```tsx
useEffect(() => {
  document.title = confirmed
    ? 'Intake Submitted | Patient Portal'
    : 'AI Intake | Patient Portal';  // ← always "AI Intake" even when mode === 'manual'
  return () => { document.title = 'Patient Portal'; };
}, [confirmed]);  // ← mode is not a dependency
```

When a patient switches to Manual mode, the document title and browser tab continue to read "AI Intake". Screen reader users and users who rely on tab titles for navigation context receive incorrect information. WCAG 2.4.2 (Level AA) requires a descriptive title that matches the current page state.

**Required fix:**
```tsx
useEffect(() => {
  if (confirmed) document.title = 'Intake Submitted | Patient Portal';
  else if (mode === 'manual') document.title = 'Manual Intake Form | Patient Portal';
  else document.title = 'AI Intake | Patient Portal';
  return () => { document.title = 'Patient Portal'; };
}, [confirmed, mode]);
```

## Informational Notes

### CR-014

**Severity:** ℹ️ INFO
**File:** `frontend/src/hooks/useAIIntake.ts`
**Lines:** 322–328
**Category:** Architecture

**Observation:** `confirmIntake` submits `capturedFields` to the backend:

```ts
body: JSON.stringify({ appointmentId, capturedFields })
```

After `stripPhiValues` runs on every `saveToStorage` call, the `capturedFields` in _memory_ (state) still hold the original PHI values that were typed by the patient. This is by design — the in-memory state is needed for the summary review display. However, there is no client-side check that all non-`manualRequired` fields have non-empty `value` strings before `confirmIntake` fires. A field could be empty if `saveToStorage`'s stripped copy was accidentally used to restore state.

**Not a defect** — this is a documentation gap. Consider adding a `capturedFields.every(f => f.manualRequired || f.value)` guard before calling `confirmIntake`.

### Anti-Patterns Detected

- **Misleading comment (CR-004):** `// N-004: AbortController prevents React StrictMode double-invoke side-effects` — the comment documents intended behaviour that is not implemented, creating a false sense of correctness.
- **Implicit feature flag via `import.meta.env.DEV` (CR-005):** Using the build-mode flag for feature control rather than an explicit feature flag variable couples deployment configuration to development convenience.

### Architectural Concerns

- **Context default as implicit provider (CR-002):** Using `createContext(devDefault)` as an authentication source (rather than an explicit `AuthProvider` component) makes the auth flow invisible to readers of `App.tsx`. Any new route or hook consumer will silently get dev credentials in DEV and null in production.
- **AbortController lifecycle mismatch (CR-004):** The AbortController is scoped to the `startSession` function call, but its lifecycle should span the component mount. This is a fundamental lifecycle architecture issue, not just a missing `abort()` call.
