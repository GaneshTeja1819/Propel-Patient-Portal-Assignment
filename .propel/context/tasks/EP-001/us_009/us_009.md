# User Story - US_009

## Story ID
* ID Format: US_009

## Story Title
* Patient Self-Registration with Email Validation

## Description
* As an unauthenticated user, I want to create a patient account using a valid email address and a compliant password, so that I can access the appointment booking and intake features without staff involvement.

## Acceptance Criteria

### AC-001: Successful self-registration creates account and audit entry
- **Given**: An unauthenticated user is on the registration page and the email address is not already registered
- **When**: The user submits a valid email, a password meeting complexity rules, and all required profile fields
- **Then**: A Patient account is created with a hashed password and Patient role; an immutable audit log entry is written for the registration event; the user is redirected to the login page with a success message (UC-001)

### AC-002: Duplicate email returns error without disclosing account existence
- **Given**: The submitted email address already exists in the system
- **When**: The user submits the registration form
- **Then**: A validation error is displayed ("Email address already in use"); no indication is given as to whether the email belongs to a Patient, Staff, or Admin account; no partial account is created (UC-001 Extension 2a)

### AC-003: Password complexity failure returns specific feedback
- **Given**: The submitted password does not meet complexity rules (e.g., fewer than 8 characters, no uppercase letter)
- **When**: The user submits the registration form
- **Then**: The specific failing complexity rule is displayed inline beside the password field; the form is not submitted; focus remains on the password field (UC-001 Extension 2b)

### AC-004: Database failure returns generic error without partial account
- **Given**: The database write fails during account creation (simulated with a mocked DB error)
- **When**: The user submits a valid registration form
- **Then**: A generic error message is displayed ("Registration failed — please try again"); no partial User record exists in the database; no audit log entry is written for the failed attempt (UC-001 Extension 3a)

### AC-005: Form fields meet accessibility requirements
- **Given**: The registration page is rendered
- **When**: An axe-core scan is run against the page
- **Then**: Every form input has a visible label associated via `htmlFor`/`id`; every validation error is linked via `aria-describedby`; zero axe label violations are reported (UXR-203, UXR-204)

## Edge Cases
* User submits a registration form twice in rapid succession (double-click) → server-side idempotency check prevents duplicate account creation; the second request returns HTTP 409 with an appropriate message
* Email address contains unicode characters → input is normalised to ASCII-compatible encoding before uniqueness check; if normalisation fails, a validation error is shown
* Registration page loaded on 375px mobile viewport → no horizontal scroll; all inputs and CTA are fully visible and touch-target ≥ 44 × 44 px
