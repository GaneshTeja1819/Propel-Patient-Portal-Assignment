# User Story - US_010

## Story ID
* ID Format: US_010

## Story Title
* User Login with JWT and Role-Based Redirect

## Description
* As a registered user (Patient, Staff, or Admin), I want to log in with my email and password and be redirected to my role-specific dashboard, so that I can immediately access the features relevant to my role without extra navigation steps.

## Acceptance Criteria

### AC-001: Successful login issues JWT and redirects to role dashboard
- **Given**: A valid, active account exists with matching credentials for the submitted email and password
- **When**: The user submits the login form
- **Then**: A JWT access token is issued in an HttpOnly Secure SameSite=Strict cookie; a successful login audit event is written; the user is redirected to the Patient dashboard (SCR-003), Staff queue (SCR-011), or Admin panel (SCR-015) based on their role (UC-002)

### AC-002: Invalid credentials return generic message without field disclosure
- **Given**: The submitted password does not match the stored hash
- **When**: The user submits the login form
- **Then**: A generic "Invalid email or password" message is displayed; no indication is given of which field is incorrect; the failed-attempt counter for the account is incremented by 1 (UC-002 Extension 3a)

### AC-003: Deactivated account returns generic error
- **Given**: The account exists but has been deactivated by an Admin
- **When**: The user submits valid credentials
- **Then**: A generic "Invalid email or password" message is displayed; no indication is given that the account is deactivated; the failed-attempt counter is not incremented for deactivated accounts (UC-002 Extension 3b)

### AC-004: Account lockout triggers after threshold and sends notification
- **Given**: The failed-attempt counter for an account reaches the configured threshold (e.g., 5 consecutive failures)
- **When**: The next failed login attempt occurs
- **Then**: The account is temporarily locked; a notification email is sent to the registered address; subsequent attempts (correct or incorrect credentials) return a "Account temporarily locked" message until the lock expires (UC-002 Extension 3c)

### AC-005: Login form meets accessibility requirements
- **Given**: The login page is rendered at all breakpoints
- **When**: An axe-core scan and keyboard-only navigation test are run
- **Then**: All form fields have visible labels; inline validation errors are linked via `aria-describedby`; the form is fully operable via keyboard with a visible focus ring (UXR-203, UXR-204)

## Edge Cases
* User submits login while a previous login request is in-flight (network retry) → server-side idempotency ensures only one JWT is issued; second request reuses the active session
* User's browser blocks cookies → login succeeds server-side but the JWT cookie is not stored; the React SPA detects an unauthenticated state and displays a "Cookies required" message
* Capitalisation difference in email (e.g., User@Example.com vs user@example.com) → email comparison is case-insensitive; the same account is matched
