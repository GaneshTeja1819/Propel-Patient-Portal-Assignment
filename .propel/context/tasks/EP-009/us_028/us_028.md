# User Story - US_028

## Story ID
* ID Format: US_028

## Story Title
* Data Conflict Detection and Staff Review

## Description
* As a Staff member, I want to be alerted when the AI detects conflicting clinical data values across multiple documents and resolve each conflict by selecting the authoritative value, so that the patient profile always reflects accurate, clinician-verified information.

## Acceptance Criteria

### AC-001: Conflicts are surfaced on the staff patient profile screen
- **Given**: The de-duplication pipeline has detected two or more conflicting values for the same clinical field (e.g., two blood pressure readings from the same date in different documents)
- **When**: Staff navigates to the Staff Patient Profile screen (SCR-013)
- **Then**: A dedicated "Conflicts" section is displayed listing each conflict with the severity level, conflicting values, and source document references (FR-035, UC-022, UXR-404)

### AC-002: Staff selects the authoritative value to resolve a conflict
- **Given**: A conflict is visible in the Conflicts section
- **When**: Staff selects one value as authoritative and clicks "Resolve"
- **Then**: The selected value is stored as the canonical value; the conflict record status is updated to "Resolved"; the Staff actor's ID and timestamp are recorded in the audit log; the resolved value immediately appears in the corresponding clinical section (UC-022)

### AC-003: Staff can mark a conflict as Reviewed-Unresolved
- **Given**: Staff cannot determine which value is authoritative without additional clinical context
- **When**: Staff selects "Mark as Reviewed — Unresolved"
- **Then**: The conflict status is set to "ReviewedUnresolved"; the conflict remains visible in the Conflicts section with a "Reviewed — no resolution" label; the audit log records the Staff decision and timestamp

### AC-004: No-conflicts state hides the Conflicts section entirely
- **Given**: A patient's de-duplication pipeline found no conflicts
- **When**: Staff navigates to the Staff Patient Profile screen
- **Then**: The Conflicts section is not rendered; no empty state placeholder is shown for conflicts; the clinical sections render as normal (UC-022 Extension 1a)

### AC-005: Conflict resolution is blocked for Patient-role users at the API
- **Given**: An authenticated Patient sends a request to the conflict resolution endpoint
- **When**: The API evaluates the request
- **Then**: The API returns HTTP 403; no conflict record is modified; the PatientPolicy denies the request

## Edge Cases
* Two Staff members attempt to resolve the same conflict simultaneously → the second resolve returns HTTP 409 "Conflict already resolved"; the first Staff member's resolution stands; the second Staff member sees the updated conflict state on page refresh
* All conflicts for a patient are resolved in one action (batch resolve is not a feature) → Staff resolves conflicts one at a time; after the last conflict is resolved, the Conflicts section disappears on next page load
* A new document upload triggers extraction that creates new conflicts after existing ones were resolved → the new conflicts appear in the Conflicts section with "New" badges; previously resolved conflicts remain in a "Resolved" collapsed view
