# User Story - US_002

## Story ID
* ID Format: US_002

## Story Title
* Scaffold .NET 8 Clean Architecture Web API

## Description
* As a developer, I want a scaffolded ASP.NET Core 8 Web API following Clean Architecture layering deployed to MonsterASP/IIS, so that all backend feature work starts from a consistent, testable, and dependency-isolated foundation with REST versioning enforced.

## Acceptance Criteria

### AC-001: Solution compiles and deploys to MonsterASP IIS
- **Given**: The .NET 8 solution contains Domain, Application, Infrastructure, and API projects with correct layer references
- **When**: The GitHub Actions pipeline runs the publish step
- **Then**: The solution compiles without errors; the published artefact deploys to MonsterASP IIS and responds to a health-check `GET /api/v1/health` with HTTP 200

### AC-002: Clean Architecture layer dependency rules enforced
- **Given**: Domain, Application, Infrastructure, and API layers are separate .NET projects
- **When**: Any Infrastructure or API layer attempts to reference Domain other than through interfaces
- **Then**: The compiler enforces the direction: Domain ← Application ← Infrastructure ← API; direct domain-to-infrastructure coupling results in a build error

### AC-003: REST API versioning is active
- **Given**: The API is running on MonsterASP
- **When**: A request is made to `/api/v1/health`
- **Then**: The endpoint responds with HTTP 200; a request to `/api/health` (without version prefix) returns HTTP 404 confirming version prefix is mandatory (TR-016)

### AC-004: OpenAPI / Swagger document is generated
- **Given**: The Swashbuckle package is configured in the API project
- **When**: A browser navigates to `/swagger/index.html` in a development environment
- **Then**: The Swagger UI renders; all registered endpoints are listed with HTTP method, route, and response schema

### AC-005: xUnit test project executes in CI
- **Given**: An xUnit test project exists referencing the Application layer
- **When**: The CI pipeline runs `dotnet test`
- **Then**: All tests pass; test results are reported in the CI summary (NFR-012)

## Edge Cases
* IIS application pool recycles unexpectedly → health-check endpoint returns HTTP 503; application pool restart is logged in IIS event log; CI deployment gate fails if health-check does not return 200 within 60 seconds after deployment
* MonsterASP free-tier memory limit reached → application returns HTTP 503; CI gate alerts on sustained 503 response
* Solution references a Linux-only API → CI build targeting Windows IIS fails with a descriptive compile error (TR-018 constraint)
